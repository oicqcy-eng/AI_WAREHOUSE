# 归档学习

处理 **两处 inbox** 的新资料。本 skill **不做复杂开发**，只负责判断资料放哪里、怎么总结、沉淀到哪里。

## 工作流

### 1. 读取新资料

扫描以下位置（按最近修改时间排序）：

- `delivery/inbox/`（全局总入口）
- `delivery/projects/<项目>/input/inbox/`（各项目分流区）

对每份资料执行下面的判断流程。

### 2. 判断归属（先判断放哪个体系）

| 资料特征 | 归属 |
|----------|------|
| 属于某客户项目的现场资料/需求/数据 | `delivery/projects/<项目>/` |
| 可跨项目复用的行业知识/方法论 | `docs/industry-knowledge/`（L1） |
| 可跨 Agent 复用的能力/工具/模板 | `agent/_shared/`（L2）或 `skills/` |
| 无法判断归属 | 标记 **待确认**，不强行归档 |

> ⚠️ 无法判断时**先列为待确认**。错误归档比不归档更难清理——资料进了错位置，后面的人会以为是真相。

### 3. 判断资料类型

| 类型 | 归档到 |
|------|--------|
| 需求 | `<项目>/input/requirements/` |
| SQL | `<项目>/input/sql/` |
| 报表页面 | `<项目>/input/report_ui/` |
| 接口 | `<项目>/input/interfaces/` |
| 问题复盘 | `<项目>/knowledge/` |
| 交付输出 | `<项目>/output/` |

### 4. 复制归档（保留原件）

- **复制**资料到目标目录，**不删除 inbox 原始文件**
- 命名规范：`<主题>_<日期>_<版本>.<ext>`，不改名覆盖
- 归档完成后 inbox 原件保留（供追溯），定期由人确认后清理

### 5. 学习分析（提炼知识）

对资料提炼以下要素，生成**知识卡片**：

- **业务对象**: 涉及的核心业务实体
- **字段口径**: 关键字段的定义、单位、口径
- **接口规则**: 接口路径、参数、协议
- **页面要求**: 报表/看板的结构、字段、更新频率
- **待确认项**: 资料中不明确、需向客户确认的内容

### 6. 更新知识库

- **通用经验** → `docs/industry-knowledge/` 或 `agent/_shared/`（可复用才放）
- **项目独有** → `delivery/projects/<项目>/knowledge/`
- 边界不清楚 → 标记 **待确认**，不猜测归属
- 知识卡片登记到对应 `knowledge/README.md` 的索引

### 7. 标注来源与防幻觉

- **每个结论必须注明来源文件**（`来源: <文件路径>`）
- 不确定内容标记 **待确认**
- **不捏造**：表名、字段、接口、客户结论一律以资料原文为准
- 资料里没有的细节，禁止脑补

## 输出格式

对 inbox 每份资料输出处理记录：

```
## <资料文件名>
- 归属: <项目名> / 通用 / 待确认
- 类型: <需求/SQL/报表/接口/复盘/输出>
- 归档位置: <目标路径>
- 知识卡片: <提炼的要素摘要，注明来源>
- 待确认项: <列出的问题>
```

## 检查清单

- [ ] 每份资料都有归属判断（含待确认）
- [ ] inbox 原始文件未删除
- [ ] 归档路径符合 `delivery/` 结构规范
- [ ] 知识提炼带来源标注
- [ ] 无捏造的表名/字段/接口/客户结论
- [ ] 待确认项已显式列出
