**核心原则**：遇到仓库治理问题时，第一反应是"写入点有什么约束缺失"，而不是"如何清理现有问题"。

**Why**：本轮验证了多次——tmp/ 从 10,987→8,396（事后清理一次），写入时分类规则（源头治理永久生效）；BUILDING.md 重复写入（修复 hook 源头，不再重复）；Skills 双目录（删除根级镜像，单源唯一）。事后治理只是推迟问题，源头治理才是根治。

**量化依据**：breakeven 分析——事后治理成本 O(n×周期)，源头治理成本 O(1+写入次数×决策成本)。本仓库日均 tmp/ 写入 20-50 次，远超 180 次 breakeven 点，源头治理显著更优。

## 决策框架（按顺序思考）

1. **识别写入点**：这个症状的源头在哪里？
2. **评估修复成本**：
   - 修复写入点成本 < 持续事后治理成本 → 优先源头治理
   - 历史包袱过大、修复成本过高 → 只修源头，接受历史
   - 根因不明确 → 先观察，不急于约束
3. **检查边界条件**：写入频率是否足够高？规则是否简约？是否与现有规则冲突？

## 决策矩阵

| 场景 | 首选策略 | 本轮示例 |
|------|---------|---------|
| 写入时无约束 + 高频发生 | 源头约束 | tmp/ 写入时分类 |
| 写入后有累积 + 历史包袱大 | 源头修复 + 接受历史 | BUILDING.md 去重（修 hook，保留历史） |
| 根因不确定 | 先观察，后约束 | 知识卡片过期检测（尚未明确定义） |
| 历史编号过多且引用复杂 | 规范未来 + 不修历史 | file_index 命名（不改现有编号） |

## 四个边界条件（原则失效的场景）

1. **历史包袱过大**：修复历史成本 > 接受历史成本 → 只修源头
2. **根因不确定**：定义/机制未明确 → 先观察，不急于约束
3. **写入频率极低**：月度 1-2 次写入 → 事后清理成本更低
4. **规则复杂度 > 5 条**：规则本身成为新技术债 → 精简或放弃

## How to apply

- 写代码前：考虑"这个文件最终归宿在哪里"
- 写日志/任务前：考虑"这条信息属于 worklog 还是知识卡还是 output"
- 创建任何文件时：先问"谁会在未来需要它？放在哪里最合理？"
- 发现问题时：先找"写入点缺了什么约束"，再想"如何清理现有问题"
