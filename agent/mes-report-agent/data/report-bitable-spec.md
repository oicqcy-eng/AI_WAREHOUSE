# 汇报多维表格 · 结构规范（v2.0 定型版）

> **用途**: 本文件是「原始工作日志 / 任务问题归集池」两张飞书多维表格的**唯一权威结构定义**。
> - 对用户: 重建/规范化飞书表格的蓝图（字段/类型/选项/视图/仪表盘/填报规则）
> - 对 Agent: `mes-report-agent` 读取数据时的数据字典（字段口径、取数逻辑）
> - **原则**: 日志做事实记录，任务池做项目管理，仪表盘做管理展示，AI Agent 做汇报生成。
> - **来源**: 融合豆包V1 / ChatGPT优化 / ChatGPT二次(三层架构) / 豆包最终融合 四版建议 + 266条实际数据诊断。

---

## 0. 三层架构

```
┌─────────────────────────────────────────────┐
│  AI 项目管理 Agent（mes-report-agent）        │
│  ↓ 读取 项目档案+日志+任务池+历史汇报           │
│  ↓ 分析 本周完成/风险/延期/需领导决策           │
└─────────────────────────────────────────────┘
                   ↑
┌─────────────────────────────────────────────┐
│  汇报输出层：周报 / 月报 / 总监简报 / 仪表盘    │
└─────────────────────────────────────────────┘
                   ↑ 主数据源
┌─────────────────────────────────────────────┐
│  任务问题归集池（管理核心：风险/进度/生命周期）  │
└─────────────────────────────────────────────┘
                   ↑ 佐证素材
┌─────────────────────────────────────────────┐
│  原始工作日志（每日客观流水，不承载管理属性）    │
└─────────────────────────────────────────────┘
```

**核心逻辑**：周报/月报/高层汇报**主数据源 = 任务池**；原始日志仅作任务的过程佐证，**不单独出汇报**（避免碎片化工作量汇报）。

## 1. 表 1「原始工作日志」—— 轻量化，员工自用

**定位**: 每日客观流水。只记录「今天做了什么」，不承载风险/进度/验收标准等管理属性。
**填报主体**: 一线实施人员（责任人）。**总字段 12 个（必填 5 + 可选 7）**，视图 3 个。

> **「必填」列的判据**：以 `tools/worklog-schema.js` 的 `LOG_REQUIRED`/`TASK_REQUIRED` 为准——那是**写入路径的硬校验**，缺了直接抛错。
> 本表另有的 ✅ 只作填表引导；程序不拦的项在下方单独标注。

### 1.1 字段定义

| # | 字段名 | 类型 | 必填 | 选项 / 说明 |
|---|--------|------|:----:|------------|
| 1 | 记录日期 | 日期 | ✅ | 默认今日，无需手填 |
| 2 | 所属项目 | 单选 | ✅ | **7 项**（厂区/系统粒度，全厂共用一套口径；客户级、项目级的横切事务归入兜底值 `华纬其它项目`）—— 取值见 `tools/worklog-schema.js` 的 `OPTIONS.projects` |
| 3 | 工作内容 | **多行文本** | ✅ | **改 T1 文本**，释放历史 250 个单选选项为纯文本；自由描述当天工作 |
| 4 | 结果类型 | 单选 | ✅ | **8 项**（AI 分析的关键维度），**无缺省——必须当场判定** —— `OPTIONS.resultTypes` |
| 5 | 是否形成任务 | 单选 | ✅ | **2 项**（是/否）—— **表1→表2 的唯一入口信号**；选「是」则管理员当周收口进任务池。`OPTIONS.yesNo`。无兜底（原 `否` 兜底是死代码，2026-09-12 删除） |
| 6 | 业务模块 | 单选 | | **11 项**，**严格限定为 MES 功能模块**（不承载「工作性质」与非 MES 业务域），**无缺省** —— `OPTIONS.modules` |
| 7 | 项目阶段 | 单选 | | **6 项**，**严格限定为实施方法论阶段**（不承载项目生命周期状态），**无缺省** —— `OPTIONS.stages` |
| 8 | 责任人 | 单选 | | 默认当前用户 |
| 9 | 关联任务 | 文本 | | `T-xxx`，逗号分隔可多值；写入时校验引用是否存在 |
| 10 | 协作人 | 多选 | | 可多人 |
| 11 | 交付产出 | 文本 | | 这条工作产出的实物/文档/数量，如「安装点位 10 个」 |
| 12 | 附件 | 附件 | | 截图/文件 |

### 1.2 三套视图

| 视图 | 筛选规则 | 用途 |
|------|----------|------|
| 我的日报 | 记录日期=今日 AND 责任人=当前用户 | 员工个人导出日报 |
| 项目周流水 | 记录日期∈本周，按所属项目分组 | 管理员溯源任务配套日志 |

## 2. 表 2「任务问题归集池」—— 管理核心，汇报主数据源

**定位**: 承载任务**全生命周期**（发现→计划→闭环→标准）。**所有管理类汇报的主数据源**。
**维护主体**: 项目管理员（**不开放一线绑定**，权限集中收口）。**总字段 14 个**，视图 4 个。

### 2.1 字段定义（基础 + 生命周期 + 管理管控三类）

**A. 基础字段**

| # | 字段名 | 类型 | 必填 | 选项 / 说明 |
|---|--------|------|:----:|------------|
| 1 | 归集标题 | 文本 | ✅ | 规范格式：**【项目简称-业务模块-核心问题】**，如 `三厂小簧-设备数采-现场点位电源未接` |
| 2 | 对应项目 | 单选 | ✅ | 与表1口径一致（7项）|
| 3 | 问题来源 | 单选 | ✅ | **6 项**（**暴露渠道**维度）—— `OPTIONS.sources`。注意 `问题管制表` 是**承载台账**不是渠道，**不是合法值** |
| 4 | 优先级 | 单选 | ✅ | **P1/P2/P3/P4（4 项）**：<br>P1 停线/重大风险 · P2 重大异常/跨月延期 · P3 一般问题 · P4 优化建议 —— `OPTIONS.priority` |

**B. 生命周期字段**

| # | 字段名 | 类型 | 必填 | 说明 |
|---|--------|------|:----:|------|
| 5 | 发现日期 | 日期 | ✅ | 问题首次暴露日（原「记录日期」改名，明确语义）|
| 6 | 计划完成日期 | 日期 | 建议 | 承诺闭环日。**不在 `TASK_REQUIRED` 内，也无兜底**——2026-09-12 拍板**保持不必填**：未知即留空，优于为没谈定的日期造一个假承诺（与已删的 3 条兜底同一类伪造）。实测 219 条任务中 133 条为空、未闭环 94 条中 62 条为空；`export-range` 遇空打印 `计划—`，降级不崩 |
| 7 | 实际闭环日期 | 日期 | | 状态变「已闭环」当日（原「完成日期」改名）|
| 8 | 任务状态 | 单选 | ✅ | **4 项**（无「已完成」态，闭环即 已闭环+实际闭环日期）—— `OPTIONS.taskStatus` |
| 9 | 进度百分比 | 数字 | | 0~1 或 0~100% |
| 10 | 闭环判定标准 | 文本 | | **「什么算完成」**，如「数采点位通电+数据进 MES」；缺失则闭环争议时无依据 |

**C. 管理管控字段**

| # | 字段名 | 类型 | 必填 | 说明 |
|---|--------|------|:----:|------|
| 11 | 周报归集分类 | 单选 | ✅ | **5 项**（AI 分块依据）—— `OPTIONS.weekCat` |
| 12 | 协调资源需求 | 文本 | | 需领导/跨部门支持事项 |
| 13 | 关联日志 | 关联(多) | | 管理员每周**批量绑定**本周相关日志（一对一任务 ↔ 多条日志）|
| 14 | 附件 | 附件 | | 佐证材料 |

### 2.2 四套视图

| 视图 | 筛选规则 | 用途 |
|------|----------|------|
| 项目任务总览 | 按对应项目 + 任务状态 双层分组 | 日常进度管控 |
| 周报素材 | **本周新建 OR 任务状态变更日期∈本周**，按优先级排序 | AI 生成周报主数据源 |
| 月报素材 | 本月新增 / 本月闭环 / 跨月未闭环 | 月度台账 |
| 高层风险 | 优先级∈P1/P2 AND 状态≠已闭环 | 直接截图给领导 |

> 注: 周报/月报取数**按日期条件筛选**（创建/状态变更日），**不新增手动打标字段**——避免额外维护成本。

## 3. 仪表盘（1 套总驾驶舱）

**定位**: 给厂长/总监看，**放弃"今日/本周完成多少条日志"的工作量统计**。

| 模块 | 指标 |
|------|------|
| ① 各项目健康度 | 总任务数 / 进行中 / 已闭环 / 延期数量 |
| ② 风险分级看板 | P1/P2/P3 未闭环数量（P1 单独卡片置顶预警）|
| ③ 业务模块实施进度 | 物料管控 / 设备数采 / 安灯 / U9接口 等完成率 |
| ④ 本周重点待协调 | 自动抓取任务池「协调资源需求」非空项 |

**视图总数 ≤ 8**：日志 3 + 任务池 4 + 仪表盘 1 = 8，防止视图泛滥。

## 4. 填报规则

### 4.1 日志填报（一线员工，≤1分钟/条）
1. 记录日期（自动）、所属项目、工作内容、结果类型、是否形成任务 —— 5 项必填
2. 业务模块/项目阶段/协作人/附件 —— 有就填，没有不填
3. **不开放**任务绑定：员工只需判断「是否形成任务=是/否」，不选具体任务

### 4.2 任务池准入规则（管理员判断哪些日志进任务池）
**进任务池**：停线风险 / 跨部门协调 / 系统BUG / 需求变更 / 领导关注事项 / 审厂要求
**不进任务池**：普通会议 / 日常测试 / 简单配置 / 常规培训
（对应「是否形成任务=是/否」）

**AI 主动判定（2026-08-10 用户定版）**：AI 在分析日志/纪要/数据时，**主动用专业判断识别「非流水账」事项**——有意义的、需汇报的、可汇报的（含拿不准是否该汇报的），识别出的**都主动形成任务表数据**，不依赖用户显式标记「是否形成任务=是」。即：即使日志标「否」、或用户未提建任务，只要 AI 判定该事项有跟进价值（不是日常流水账），就主动建任务。**宁建不漏**——任务池是管理抓手，多建的项可暂缓/降级（P4），漏建则错失跟进。

### 4.3 管理员每周收口动作（固定 1 次，约 15 分钟）
1. 表1 筛本周 `是否形成任务=是` 的记录
2. 表2 批量绑定关联日志（一对一任务 ↔ 多条日志）
3. 更新任务池状态/进度/周报归集分类
4. 确认 P1/P2 未闭环项 → 自动出现在「高层风险」视图

### 4.4 缺省值策略（用户聊天未明确/遗漏时取最低档）

**字段解读优先级（2026-08-10 用户定版）**：
1. 优先**从用户描述/分享信息解读**最合适的选项（如「扫码上料卡住」→ 业务模块=物料管控、结果类型=风险暴露）
2. 解读不到看**上下文推断**（项目/协作人/日期尽量自己定）
3. **拿不准/关键字段有实质分歧**（结果类型/是否形成任务/优先级/业务模块/项目阶段）→ **直接问用户给选择**，不硬猜
4. 确实无信息才落兜底（下表）

> 原则：**尽可能解读、拿不准就问、宁可问不硬猜**。兜底只在第 4 步用，不是默认路径。

**有兜底**（均为「排序/分组归位」，非事实断言）：

| 字段 | 兜底值 | 理由 |
|------|--------|------|
| 优先级（表2） | `P4` | 序的末位 |
| 任务状态（表2） | `待启动` | 生命周期初态；新建任务**确实**尚未开始 |
| 周报归集分类（表2） | `长期跟踪` | 分组归位：未归类 → 不进本周正文 |
| 责任人 | `陈宇` | 单人仓库，恒等于本人（声明式兜底，非静默） |
| 所属项目 | 上下文推断；推断不了则询问 | 猜错会污染汇报口径 |
| 记录日期 | 今天 | 补录旧日期需用户说明 |

**无兜底——必须当场判定，判不了就问用户，留空优于填假值**：

| 字段 | 原兜底值 | 为什么删 |
|------|----------|----------|
| `结果类型` | ~~`需求确认`~~ | 种类断言。实测曾占 **54.1%**，"我没判断"被伪装成"我判断了"，下游无法区分。**仍保持必填** |
| `项目阶段` | ~~`需求调研`~~ | 阶段断言。实测曾占 **46.5%** |
| `业务模块` | ~~`系统管理`~~ | 种类断言（dashboard 模块分布的分子） |

> 判据：兜底合法当且仅当它是下游排序/分组/状态机的单位元；是「事实断言」则禁止。反例：`项目阶段` 看似序列初态，但日志记录的是**已发生的工作**，不可能"尚未开始"——而任务 `待启动` 是构造性事实。
> ✅ 2026-09-12 追加删除两条**死兜底**：`问题来源='会议决策'`、`是否形成任务='否'`。
> 它们与上表同属伪造，但更隐蔽——必填校验跑在补兜底之前，所以**在写入路径上永远不可达**（实测：不传必填项直接抛错，兜底救不了）。
> 真正的风险是将来谁把该字段移出 `*_REQUIRED`，这条伪造兜底会**突然激活**。删除前后行为零变化。
> 现存兜底只剩**非必填**字段：日志 `责任人='陈宇'`；任务 `任务状态='待启动'`、`周报归集分类='长期跟踪'`、`发现日期=当天`。

### 4.5 模块上线进程日志（2026-08-10 用户定版）

**目的**：看日志表一眼看出整个项目**模块上线进程**（启动→收集资料→培训→上线运行）。

**规则**：
1. 日志出现**新功能模块**或模块进入**新里程碑阶段** → 为该模块单独列一条进程日志（同项目同模块一条）
2. 工作内容以 **`【模块上线进程】`** 开头（一眼可辨）
3. 模块新阶段 → `update-log` **扩充该条**（保留历史阶段，追加新进展），一条承载全部进程
4. `业务模块`=该模块；`项目阶段`=模块当前阶段；`是否形成任务`=否（进度追踪非问题任务）
5. **枚举外模块**：`业务模块`枚举里没有的模块（如未来追溯/SPC/安灯报表等）→ **扩展枚举**，先在枚举定义处新增该项，再建进程日志；不硬塞相近项（会错分类污染统计）。
   > **枚举只有一个定义源：`tools/worklog-schema.js` 的 `OPTIONS`**（2026-09-11 修订）。
   > 旧版此处写"两处定义源（spec §1 + `worklog-server.js` `modules` 数组）"——已作废：`worklog-server.js` 的本地副本已删除并改为 require 契约模块。
   > 扩展流程：改 `OPTIONS` → 跑 `validate` → 同步各文档的「N 项」计数 → 再建日志。
   > `runbooks/bitable-fill-guide.md` 为飞书时代遗留说明，**不是定义源，也不参与校验**。

**工作内容模板**：`【模块上线进程】<项目>-<业务模块>：启动(日期/方式) → 资料收集(日期) → 培训/配置(日期) → 上线运行(日期) → 后续优化(日期)`

## 5. AI 汇报生成逻辑（mes-report-agent）

### 5.1 数据源（四件套）
```
项目基础档案（delivery/projects/<项目>/input+knowledge）
+ 原始工作日志 全量流水（表1）
+ 任务归集池 全量任务（表2）
+ 历史归档汇报（以往周报/月报）
```

### 5.2 分析维度
本周完成 / 风险 / 延期 / 需要领导决策

### 5.3 输出三件套
| 输出 | 使用者 | 内容 |
|------|--------|------|
| 项目实施周报 | 项目经理 | 本周完成事项、推进卡点、下周计划 |
| 总监精简简报 | 高层 | 仅项目进度、P1/P2风险、需跨部门决策事项（P1 置顶→P2→P3 精简→P4 折叠）|
| 月度项目复盘 | 全项目 | 月度闭环统计、遗留问题长期规划 |

## 7. 落地步骤（2026-08 已由 API 全自动建成）

## 8. API 操作教训（2026-08-08 实战沉淀）
> 详情见 memory `worklog-tools-pitfalls`（6 坑清单），本段只作飞书表维护参考。

> 给 Agent 重建/维护本表时规避的坑，避免重复踩。

### 8.1 单选字段写值必须用「选项名」，不是选项 ID

- 建字段时创建选项会返回选项 ID；但**写记录值时单选字段传「选项名」字符串**（如 `陈宇`），**不是**选项 ID（如 `optxJo1jn1`）。
- 若传了 ID，飞书会把每个 ID 当成**新选项名自动建出来** → 下拉里出现一堆 `optxxxx` 垃圾选项，记录值也指向垃圾项。
- **修复**：记录值批量从 ID 改回名称（`records/batch_update`）+ 字段 `PUT` 清理垃圾选项（只保留正常选项的 `id/name`）。
- 判断垃圾选项：选项名匹配 `/^opt[A-Za-z0-9]{7,9}$/`。

### 8.2 字段更新用 PUT，不是 PATCH

- 字段（`fields/{id}`）修改用 **PUT** + 完整对象 `{field_name, type, property}`；**PATCH 返回 404**。

### 8.3 视图排序/分组 API 不支持持久化

- 视图 property 的 `sort_info`/`group_info` PATCH 返回成功但被静默忽略；**只有 `filter_info`/`hidden_fields` 生效**。
- 排序/分组必须在飞书 UI 手动配置（见 §7）。

### 8.4 频控与重试

- 频繁调用间歇性返回 `code 9499 / 99991400` 或 `.items undefined`，需**重试 + 1-2s 延迟**；字段/视图/记录 GET 都可能触发。

### 8.5 新建表格默认附「数据表」演示空表

- 每个新多维表格自动带一个默认演示表「数据表」（默认字段+10 条空记录），可 DELETE `/tables/{id}` 删掉，避免误导。

### 8.6 记录排序不可靠

- 记录列表 API 返回顺序不等于插入顺序；验证新增记录时应**按内容搜索**，不要按位置取「最新」。

### 8.7 日期处理

- 记录日期字段传**毫秒时间戳**（`Date.getTime()`），`new Date(2026, 7, 6)`（月份 0 基，8 月=7）。

### 8.8 知识沉淀的修订机制

沉淀的知识不是死教条，过时/不适应时**修订而非抹掉**：
- 规则要变 → 改文档并**保留版本痕迹**（旧规则 + 更新时间 + 原因）
- 认知要修正 → 改正 + 追加纠错记录（"原以为X，实际Y"）
- 新方法替代 → 记新法，留旧法对照（注明弃用原因）

## 9. 汇报输出规范（2026-08-08 定版）

### 9.1 输出文件双格式

每次生成周报/月报/简报，**md + docx 双份**归档到 `delivery/projects/hw-spring-mes/output/reports/`：
- **md**：留档（进 git、AI 可读、便于对比）
- **docx**：给用户日常打开（WPS/Office 原生格式）

### 9.2 内容规范

- **不写来源信息**：不标注"生成日期/数据源/飞书表"等内部字样（对外汇报是成品，不是工具输出）
- **简报不用"总监精简"字眼**：标题为"XXX项目简报"，定位类文案去掉
- 命名：`<YYYY-MM-DD>_<周报_W周|月报_M月|简报>_<口径>.md/.docx`，不改名覆盖

### 9.3 docx 排版定稿样式（WPS 友好）

转换工具：`agent/mes-report-agent/tools/md-to-docx.js`（依赖 npm 包 `docx`，运行前需 `npm install docx`；可用第 2 参数指定输出目录）

| 项 | 定稿值 | 说明 |
|----|--------|------|
| 字体 | **微软雅黑** | 清晰专业，WPS/Office 默认，显示稳定不丢字形 |
| 大标题 | 15pt 深蓝 `#1F4E79` 居中 | 不加粗需求外装饰线 |
| 章节标题 | 12/11pt 中蓝 `#2E75B6` | 一级二级标题 |
| 正文 | 9pt | 内容紧凑 |
| 表格字号 | **8pt** | 微软雅黑 8pt 是正式汇报稳妥组合（7pt 偏挤） |
| 表格框线 | 单元格**实黑框线** + 深蓝粗外框 | WPS 下清晰可见（浅色细框线在 WPS 会"隐形"） |
| 表头 | 蓝底 `#2E75B6` + 白字加粗 | 专业汇报感 |
| 表格对齐 | **全部左对齐 + 垂直居中** | 不居中不右对齐，整齐 |
| 状态着色 | 推进快/正常→绿 `#2E7D32`，稳步/进行中→黄 `#B26B00`，阻塞/暂缓→红 `#C00000` | 简报"当前状态"列 |
| 优先级着色 | P1→红加粗，P2→深灰加粗 | 简报 P1 风险表 |
| 列宽 | 长文本列（关键看点/风险/需协调）26%，短列 10-13% | 避免文字挤乱 |

> 迭代教训：浅蓝细框线在 WPS 几乎不可见 → 必须用实黑单元格框线；微软雅黑比幼圆更适合作正式汇报（幼圆偏"可爱风"，小字号笔画细）。

### 9.4 触发规则（2026-08-10 用户定版）

| 产物 | 触发 | 说明 |
|------|------|------|
| 周报 | **每周固定** | 每周收口日（默认周五）必出 |
| 月报 | **不固定，按需手动触发** | 需要时（领导要月度口径 / 月度里程碑节点 / 月度收口）手动生成；**不作每月固定出** |
| 简报 | 需高层时手动触发 | 需高层汇报/需跨部门决策时出 |

### 9.5 周报取数口径（2026-08-10 用户定版）

**主数据源 = 任务池**（§1 核心逻辑不变）；但**日志按结果类型参与周报**——关键类日志即使「是否形成任务=否」也能上报表，避免重要工作漏报：

| 日志结果类型 | 周报去向 | 说明 |
|------|------|------|
| `风险暴露` | 周报**核心问题及风险**栏 | 即使标「否」也进风险栏（观察到的风险） |
| `问题关闭` `方案确认` `配置完成` `培训完成` `数据完成` `上线验证` | 周报**本周完成事项**栏 | 即使标「否」也进完成栏（同类归并） |
| `需求确认` | **不进周报正文** | 最低档；除非建任务进池 |

> **口径**：
> - 标「是」建了任务的日志 → 走任务池口径（完成/风险/待办按任务状态归位）
> - 标「否」但结果类型 ∈ 上表关键类 → **作为日志佐证补进对应栏**（同类归并，不碎片化）
> - `需求确认` 是最低档，默认「当日事当日毕」，不进周报正文
> - 里程碑类日志（上线验证/培训完成/方案确认等）即使没建任务，也要在周报「完成事项」体现——这是本条新增的核心价值
