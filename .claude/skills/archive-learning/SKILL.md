# 归档学习

处理 **两处 inbox** 的新资料。本 skill **不做复杂开发**，只负责判断资料放哪里、怎么总结、沉淀到哪里。

## 工作流

### 1. 读取新资料

#### 1.1 文件型资料（inbox 扫描）

扫描以下位置（按最近修改时间排序）：

- `delivery/inbox/`（全局总入口）
- `delivery/projects/<项目>/input/inbox/`（各项目分流区）

对每份资料执行下面的判断流程。

#### 1.2 图片/截图型资料（对话内投喂）

**触发条件**：用户在对话中直接粘贴/拖入图片，或说"看这张图""帮我识别这张图"。

**处理流程**：
1. 直接用 vision API 识别图片内容（OCR + 语义理解）
2. 提取关键信息（文字/表格/流程图/报错信息等）
3. 判断归属（参照 §2 归属判断表）
4. 归档到对应目录：
   - 客户投喂的原始截图 → `delivery/inbox/日常运维报错截图/` 或 `input/<厂区>/raw/`
   - 提炼出的知识 → 走 §5 提炼知识卡片
5. **不生成独立知识卡**：图片本身作为附件留本地，提炼出的结论沉淀到知识卡

**注意**：图片识别是 AI 能力，不需要 OCR 脚本。只有当图片太大/格式特殊时，才用 `.claude/skills/archive-learning/scripts/ocr.ps1` 预处理。

### 2. 判断归属（先问"以后谁会用"）

**核心启发**：先问一句「以后谁会用」。不用纠结太细。

| 资料特征 | 归属 |
|----------|------|
| 多个项目都会用（可复用模板/方法论） | 共享池：`docs/industry-knowledge/`（L1）、`agent/_shared/`（L2）、`skills/` |
| 只服务当前项目（现场资料/需求/数据） | `delivery/projects/<项目>/` |
| 无法判断归属 | 标记 **待确认**，不强行归档 |

> ⚠️ 无法判断时**先列为待确认**（登记到 `pending_questions.md`）。错误归档比不归档更难清理——资料进了错位置，后面的人会以为是真相。

### 3. 判断资料类型

| 类型 | 归档到 |
|------|--------|
| 需求 | `<项目>/input/requirements/` |
| SQL | `<项目>/input/sql/` |
| 报表页面 | `<项目>/input/report_ui/` |
| 接口 | `<项目>/input/interfaces/` |
| 问题复盘 | `<项目>/knowledge/` |
| 交付输出 | `<项目>/output/` |
| 客户原始数据（管控表/台账/报价/原始报表） | `<项目>/input/<厂区>/`，原件按铁律不入库留本地 |

> **知识 vs 动作 分流**：判断类型时先分清它是「知识」还是「动作」——
> - **知识类**（规则/口径/流程/接口/页面要求）→ 继续走第 5 步提炼知识卡片
> - **动作类**（工作日志/任务/推进计划/管控表/里程碑/待办）→ **不做知识卡片**，改用 `agent/mes-report-agent/tools/worklog-append.js` 记日志 + 更新任务池
> - 拿不准时**宁做日志不做卡片**（卡片污染难清理，日志随时可补）

### 4. 复制归档（保留原件）

- **复制**资料到目标目录，**不删除 inbox 原始文件**
- 命名规范：`<日期>_<主题>.<ext>`（如 `2026-08-24_MES周报_0817-0821_汇报版.md`），不改名覆盖；同主题多版以日期区分
- 归档完成后 inbox 原件保留（供追溯），定期由人确认后清理

### 4.5 二进制文件入库边界

仓库 `.gitignore` 全局忽略 `*.xlsx/*.xls/*.docx/*.pptx/*.pdf/*.png/*.jpg` 等二进制原件（客户原始资料不入库原则）。归档时区分：

| 情形 | 处理 |
|------|------|
| 客户提供的原始二进制（管控表/台账/PPT/PDF） | **留本地** `input/<厂区>/`，不强制入库；其提炼出的整理成果（MD/知识卡/SQL）入库 |
| 我们自己产出的二进制（转换的 DOCX/渲染的 HTML） | 按先例**可 `git add -f` 强制入库**（如周报 DOCX/HTML） |
| 不确定 | 问用户，不擅自 -f |

### 5. 学习分析（提炼知识）

对资料提炼以下要素，生成**知识卡片**：

- **业务对象**: 涉及的核心业务实体
- **字段口径**: 关键字段的定义、单位、口径
- **接口规则**: 接口路径、参数、协议
- **页面要求**: 报表/看板的结构、字段、更新频率
- **待确认项**: 资料中不明确、需向客户确认的内容

### 5.1 文件命名规范检查（针对 file_index.md）

在归档 process 中，若涉及 file_index.md 条目编号，需检查命名规范：

- 项目级（delivery/projects/<客户>/input/<厂区>/knowledge/file_index.md）：使用 `F-0xx` 格式
- 资产库级（agent/mes-implement-expert/data/<system>/file_index.md）：使用系统前缀（如 `SQL-0xx`、`U9-0xx`、`LIMS-0xx`）

若发现不符合规范的条目，应在归档前进行修正或标记为待确认。

### 6. 更新知识库（写入四件套）

**通用经验** → `docs/industry-knowledge/` 或 `agent/_shared/`（可复用才放）

**项目独有** → 写入 `delivery/projects/<项目>/knowledge/` 四件套：

| 文件 | 写入内容 |
|------|----------|
| `file_index.md` | 归档资料登记一行（编号/文件/类型/来源/日期/状态） |
| `knowledge_cards.md` | 提炼的知识卡片（五要素 + 来源） |
| `pending_questions.md` | 待确认问题登记（编号/问题/涉及资料/日期/状态） |
| `delivery_notes.md` | 交付建议、注意事项、后续可复用标签（经验沉淀） |

- 边界不清楚 → 标记 **待确认**，登记到 `pending_questions.md`，不猜测归属
- **经验不滞留**: 可复用的跨项目经验（工序编码/群组体系等）→ 提炼到 `docs/industry-knowledge/`，不只留在项目内

### 6.5 沉淀判断清单（把"沉淀"变成可执行）

归档完成、提炼出知识后，**逐条判断**哪些该提炼到共享层（L1），哪些留项目内：

```
□ 这个知识只服务当前项目？（客户专属名单/现场特殊配置）→ 留在项目 knowledge/
□ 别的项目也会用？（编码规则/字段口径/方法论/接口规范）→ 提炼到 docs/industry-knowledge/
□ 是从具体实例抽象出的"规律"，还是只是一堆"事实"？
   事实（这份资料的字段有哪些）→ 留在知识卡片
   规律（这类场景该怎么编码/怎么设计）→ 提炼为通用规范
□ 提炼时是否注明来源（来自哪个项目、哪张卡 K-xxx）？→ 必须注明，可追溯
□ 不确定能否复用？→ 先标"待确认"，宁可晚提炼也不乱搬
```

**沉淀产出位置**：
- 可复用编码/方法论 → `docs/industry-knowledge/<主题>.md`（如 `mes-coding-standards.md`）
- 可复用模板/工具 → `agent/_shared/` 或 `skills/`
- 提炼后项目卡片保留，L1 文件注明来源引用它

### 7. 标注来源与防幻觉

- **每个结论必须注明来源文件**（`来源: <文件路径>`）
- 不确定内容标记 **待确认**
- **不捏造**：表名、字段、接口、客户结论一律以资料原文为准
- 资料里没有的细节，禁止脑补

## 输出格式

对 inbox 每份资料输出处理记录：

```
## <资料文件名>
- 归属: <项目名> / 通用 / 待确认
- 类型: <需求/SQL/报表/接口/复盘/输出>
- 归档位置: <目标路径>
- 知识卡片: <提炼的要素摘要，注明来源>
- 待确认项: <列出的问题>
```

## 检查清单

- [ ] 每份资料都有归属判断（含待确认）
- [ ] **已判断「知识 vs 动作」**：动作类（日志/任务/计划）未误做知识卡片
- [ ] inbox 原始文件未删除
- [ ] 归档路径符合 `delivery/` 结构规范
- [ ] 二进制原件未强制入库（除非是自家产出且用户确认）
- [ ] 知识提炼带来源标注
- [ ] 无捏造的表名/字段/接口/客户结论
- [ ] 待确认项已显式列出
- [ ] 已按沉淀判断清单确认：可复用经验是否提炼到 L1（或标待确认）
